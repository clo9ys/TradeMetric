# Как данные доходят до результата

Запрос пользователя содержит список сделок. Каждая сделка остаётся отдельной строкой, даже если несколько строк имеют один ISIN. Например, покупка 10 бумаг и шорт 2 бумаг используют один снимок, но дают два результата и две записи истории.

1. API проверяет форму JSON. `StrictInt` запрещает автоматическое превращение `true`, дроби или строки в количество. Доменная проверка дополнительно запрещает ноль и выход за границы PostgreSQL BIGINT.
2. `CalculationService` фиксирует время начала расчёта и его московскую дату. `last_trading_date` приходит явно: сервис не знает праздничный и биржевой календарь.
3. `MarketDataService` ищет снимки, загруженные в этот московский день. Источник должен совпасть с выбранным: `demo`, `csv` или `cbonds`. Полнота и рыночные даты проверяются повторно.
4. Для недостающего ISIN вызывается `BondDataProvider.get_bond`. При выборе CSV файл читается один раз на экземпляр адаптера и проверяется целиком. Текстовые числа превращаются прямо в `Decimal`, даты — в `date`, строки типов — в соответствующие перечисления. `NormalizedBondData` выполняет общую доменную валидацию, такую же, как для Cbonds.
5. CSV получает время фактического чтения `fetched_at`. Даты котировки, риска и НКД берутся из файла: они не становятся сегодняшними при чтении. Несвежие данные останавливают расчёт.
6. Для каждой уникальной валюты определяется FX. RUB даёт 1 локально. Для остальных `CBRRateAdapter` запрашивает XML на дату расчёта и вычисляет `Value / Nominal`. Сохраняются дата действия из XML и отдельное время получения. Допустим более ранний действующий курс выходного дня.
7. Для каждой строки вычисляются грязная цена, стоимость в RUB и DV01. Чистая цена получает НКД ровно один раз; грязная его уже содержит. Шорт меняет знак стоимости и DV01. Для floating дюрация = `1 / coupon_frequency`, выпуклость = 0. Итог складывается алгебраически без округления строк до копеек.
8. Только после всех чтений и HTTP-запросов открывается транзакция записи. Новые снимки облигаций и валют, расчёт и все строки сохраняются вместе. Одна ошибка означает откат всех этих записей. При успехе выполняется один `commit`.
9. Ответ API содержит ID расчёта, результаты строк, источник облигации и FX с происхождением. PostgreSQL хранит связи `calculation_trades.snapshot_id → instrument_snapshots.id` и `calculation_trades.fx_snapshot_id → fx_rate_snapshots.id`. Так можно восстановить входные данные сохранённого результата.

## Зачем отдельный валютный снимок

Раньше строка расчёта уже хранила курс, дату действия и источник, но не время получения. Новая таблица сохраняет полный набор метаданных один раз на валюту внутри расчёта. Например, две USD-строки ссылаются на один FX-снимок. Между разными расчётами курсы пока не переиспользуются: таблица служит историей использованных курсов, а не постоянным кэшем.

`requested_date` — дата, на которую нужен курс. `effective_date` — дата, с которой он действует. `fetched_at` — когда приложение его получило. Эти три даты отвечают на разные вопросы и потому хранятся отдельно. В старой истории время получения неизвестно: миграция не придумывает его, ссылка на FX-снимок там остаётся пустой.

## Синтаксис, который полезно понимать

- `Protocol` описывает договор: объект должен иметь `async get_bond(isin)`. Наследоваться от `BondDataProvider` не требуется. CSV и Cbonds подходят по наличию метода с тем же контрактом; расчёт не зависит от способа получения данных.
- `async def` объявляет асинхронную функцию. `await` позволяет дождаться HTTP или БД, пока сервер может обслуживать другие запросы. Само по себе `async` не делает файловое чтение неблокирующим: поэтому CSV читается через `await asyncio.to_thread(self._read)` в рабочем потоке.
- `@dataclass(frozen=True, slots=True)` создаёт объект данных с автоматически сгенерированным конструктором. `frozen=True` запрещает обычное изменение полей, `slots=True` ограничивает набор атрибутов. Снимок представляет конкретное состояние данных, поэтому его не следует менять задним числом.
- `Decimal("101.25")` создаёт десятичное число из текста. Промежуточный `float` может внести двоичную погрешность, поэтому CSV/XML не проходят через него. Контекст Decimal имеет конечную точность; например, `1 / 3` не имеет конечной десятичной записи.
- `dict.fromkeys(isins)` убирает повторы, сохраняя порядок первого появления. Это влияет только на загрузку снимков, не на список сделок.
- `**fields` распаковывает словарь в именованные аргументы: `NormalizedBondData.from_provider(**fields)` эквивалентен передаче `isin=...`, `currency=...` и остальных полей по отдельности.
- `Callable[[], datetime]` означает функцию без аргументов, возвращающую время. В приложении это настоящие часы, в тестах — фиксированное время. Это позволяет проверять выходные и границы суток, не меняя даты учебного файла в приложении.
- `async with uow` управляет сессией БД. `flush()` отправляет записи в БД и получает их UUID, но ещё не фиксирует транзакцию. `commit()` делает изменения постоянными. Поэтому ошибка после `flush()` всё ещё может откатить весь расчёт.
- `ForeignKey(..., ondelete="RESTRICT")` связывает строку со снимком и запрещает удалить снимок, на который ссылается история. Поле `Mapped[UUID | None]` означает, что в старой истории ссылка может быть `NULL`.

Полный контракт CSV и точное правило даты НКД описаны в [backend/README.md](../backend/README.md).

## Активная рыночная выгрузка

Сейчас `.env` выбирает `bonds_market.csv` со 100 реальными флоатерами RUB и тремя fixed CNY из MOEX, `CSV_DATA_MODE=market`, `CSV_REQUIRE_MANIFEST=true`. Учебный файл не выбран. Команда `python -m scripts.refresh_bonds_csv` обновляет данные из ISS без подстановки неизвестных параметров. Соседние `.meta.json` и `.source.json` сохраняют происхождение, дату торгов и фактическое время загрузки. Служебные сведения не показаны постоянными надписями на странице расчёта, но доступны для проверки в файлах.

Для fixed CNY экспортёр получает модифицированную дюрацию, выпуклость, полную цену и НКД из одного ответа калькулятора MOEX на дату котировки. При расчёте CSV-параметры передаются в fixed-ветку без замены на формулу флоатера. CNY пересчитывается в RUB через существующий CBRRateAdapter; в БД сохраняется использованный валютный снимок.
